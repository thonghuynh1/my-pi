# Group representation on the wire and in the store

> **α amendment (ticket 14 — no LLM at rollover).** The LLM-dependent bits of the original resolution are struck; the tail-append recall mechanism and no-protocol-change decision stand. See **§α amendment** below.

## Question (original)

The existing conductor contract has a flat `GroupCommand { ids[] }`. Decide whether chunked compaction:

- Reuses `GroupCommand` as-is with digest generated by the conductor (via `host.digestOf()` or a custom broker-produced string), or
- Requires a new command variant / an additive field (e.g. `GroupCommand.summary?: string`, or a `ReplaceCommand` targeting a synthetic block).
- What does `recall` do on a member of a group summary — return the original member text, refuse, or unfold the whole group?
- Does the group need a stable identity that survives session reload (so subsequent conducts can recognize it), or is it recomputed each session?
- Do we need any additive change to the conductor protocol at all, or can this all live inside `MyCustomizeConductor`?

## α amendment (from ticket 14)

Ticket 14 resolved α (no LLM broker for group summaries). Applied to this ticket:

- **§1 command shape** — **narrows.** `GroupCommand { ids, digest }` still reused; `digest` is now a **deterministic pure function of the pre-group corpus**, not a broker-produced string. Composition: `⟨chunked-compaction · N blocks · turns X–Y · content-hash <hash>⟩\n<deterministic body>\nMembers: {#a3f9} {#b7c2} …`. Exact composition rule for `<deterministic body>` (structural aggregation vs concatenated per-block `replace` outputs vs both) lands in ticket 11 / the PRD, not this map. `host.complete()` is not called; `host.can("complete")` gate is not checked; no `groupSummaryCache`; no `pendingSummaryHashes`.

  Aside on `digest: undefined`: the engine's default recap (`digest.ts:198`, via `store.svelte.ts:745`) emits one `{#code FOLDED}` tag for the group as a whole, not per member. That gives group-level recall but not per-member recall. Since the map's standing preference requires per-member recall reversibility, the conductor still emits an explicit `digest` string with the codes footer rather than passing `undefined`.
- **§2 recall on group member (tail-append)** — **stands.** The mechanism is independent of who wrote the digest text. Recovery-codes footer derives deterministically from member ids as before; the resolver still tail-appends via synthesised `recall(<code>)` tool_call/tool_result, still leaves the frozen prefix untouched.
- **§3 stable identity across session reload** — **narrows.** Layer 1 (broker cache) is **dropped in full** — there is no cache under α because the digest is a pure function of the corpus. Reload: conductor re-reads raw blocks, re-computes the pre-group corpus hash, re-emits the same `GroupCommand` with the same deterministic digest text → byte-identical restore, KV cache warm. Layer 2 (group-membership state) is still not persisted. Corpus content-hash is still the group's stable identity.
- **§4 no protocol change** — **stands.**

### Amended consequences on the MAP

- "Broker cache, session-scoped, persisted as Layer 1" is dropped from the ticket-06 summary line in Decisions so far. Determinism replaces persistence as the immutability guarantor across reload.
- The cross-cutting note for the PRD/ADR (engine-side policy branch for group-member codes) still stands.

## Original resolution (γ-shaped — historical)

Chunked compaction v1 stays **entirely inside `MyCustomizeConductor`**, on top of the existing `GroupCommand`, with the reversibility promise re-expressed as a **tail-append recall** that never rewrites the frozen prefix.

### 1. Command shape — reuse `GroupCommand`, custom digest string

- The rollover emits a single `GroupCommand { ids: <all pre-group member ids>, digest: <broker output + deterministic recovery-codes footer> }` per rollover. No new command variant, no additive field on `GroupCommand`.
- `host.digestOf()` is **not** the source of `digest` — that returns the engine's per-kind deterministic digest, not an LLM summary. The conductor drives `host.complete()` (gated on `host.can("complete")`) and caches the returned text by content-hash of the pre-group corpus.
- The ADR/PRD will explicitly **not** introduce a `GroupCommand.recoverable: true` field. Reversibility is expressed differently (see §2) so we don't create a second reversibility path parallel to `ReplaceCommand.recoverable`.

### 2. Recall on a group member — tail-append, group summary never rewritten

The group summary sitting at the boundary of the frozen prefix is **immutable and byte-identical** for the life of the session. Recall never touches it.

**Mechanism (both agent-initiated and human-GUI-initiated):**

- The conductor **appends a deterministic recovery-codes footer** to the broker's summary text before emitting it as the `GroupCommand.digest`. The broker never sees the footer; it's a conductor concern, not a prompt concern. Format is a small trailing block (e.g. `Members: {#a3f9} {#b7c2} …`) that maps one fold code per member id.
- Fold codes in the footer **derive deterministically from the member block id** (not random, not turn-scoped). This is the price of not persisting group-membership state (§3): the same corpus reload must yield the same codes so recall resolves stably.
- When a group-member fold code is recalled — by the agent's `recall`/`unfold` tool or by a human GUI unfold — the resolver:
    1. **Does not** restore the member back into its original historical position. (This is where group-member codes diverge from normal fold codes: normal `unfold` restores in place; group-member `unfold` does not.)
    2. **Appends the full original member text into the protected tail** as a `tool_result` on a `recall(<code>)` `tool_call`/`tool_result` pair. Human GUI unfold synthesises the same tool-call/tool-result shape the agent would produce itself — one mechanism, one framing.
    3. Leaves the group summary — and every downstream block on the wire — untouched. **KV-cache prefix is preserved.**
- The tail-append block counts against `liveTokens` and the tail budget like any other tail content. Repeated recalls of the same code produce repeated tail entries; history stays canonical.

This satisfies the map's standing preference — *"Preserve `recall` / unfold reversibility on every folded block"* — without touching the frozen prefix.

**Note on precedent:** The naïve-compaction test at `app/tests/conductor.compaction-naive.test.ts:336–338` currently asserts `expect(g.digest).not.toMatch(/\{#\w+\s+FOLDED\}/)`. That's a v0 behavioural fact, not a contract we owe. Chunked compaction supersedes it, and the PRD says so explicitly — the new digest string carries a deterministic codes footer.

### 3. Stable identity across session reload — Layer 1 only

- **Persist Layer 1 (the broker cache):** `corpusHash → summary text`, session-scoped (lives with the accordion session's block history, not in conductor-local global storage). This is what makes the standing preference *"Group summaries are immutable once written — no re-summarizing prior groups"* actually hold across reloads. Without cache persistence, "immutable" would silently break on reload because LLMs aren't deterministic.
- **Do not persist Layer 2 (group-membership state):** on reload, the conductor re-reads the raw blocks, re-runs its rollover trigger against them, re-computes the pre-group corpus hash, hits the persistent cache, and re-emits the same `GroupCommand` with the same digest text. The **corpus content-hash is the group's stable identity**; a separate "group id" is unnecessary.
- **Why Layer 1 alone:** avoids coupling to accordion's session-persistence layer at the group-membership level, avoids a whole drift class ("persisted group vs current blocks disagreeing"), and produces user-visibly identical behaviour on reload.
- **Fold codes survive reload** because they derive deterministically from member ids (see §2), so recall of the same code resolves to the same member text before and after reload.

### 4. Protocol change — no

- No bump to `CONDUCTOR_PROTOCOL_VERSION`. No new commands. No new fields on existing commands.
- The ticket-10 open contract question about `era` (protocol bump vs host-automatic promotion) is a **C4 / nested-groups** problem, deferred to a future map. v1 emits flat groups only.
- Everything else — rollover trigger, four-zone accounting, broker orchestration, corpus-hash keying, the codes-footer format, the tail-append recall path — is conductor-internal.

### Cross-cutting note for the PRD/ADR

The engine's fold-code resolver gains a **policy branch for group-member codes**: normal codes → restore in place (existing behaviour); group-member codes → tail-append via synthesized `recall` tool_call/tool_result, frozen prefix untouched. That's a specification the PRD must state; it is not a change to the conductor contract itself, and does not sit inside `conductors/my-customize-conductor/`. The downstream implementation map decides which module absorbs it.
